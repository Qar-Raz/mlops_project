# Flora-Bot Guardrails Documentation

## 1. Overview
The **LightweightGuard** system provides low-latency, context-aware safety checks for the Flora-Bot API. It is designed to filter toxic content from User Inputs (prompts) and Model Outputs (LLM responses) while preventing false positives common in agricultural contexts.



## 2. Context-Aware Filtering
Standard profanity filters often flag words necessary for botanical diagnosis. This implementation modifies the default blocklist to **allow** specific "violent" terms that are benign in a plant context.

* **Allowed Terms:** `kill`, `die`, `attack`, `shoot`, `dead`, `death`
* **Reasoning:** Enables legitimate discussions about "killing weeds," "fungal attacks," or "bamboo shoots" without triggering the safety blocklist.

## 3. Validation Architecture
The system employs a two-tier validation strategy to balance speed and accuracy.

### Tier 1: Optimized Regex (High Priority)
Specific safety categories are detected using pre-compiled Regular Expressions. This layer handles the most critical violations instantly.

* **Optimization:** Utilizes word boundaries (`\b`) to prevent the "Scunthorpe Problem" 
* **Blocked Categories:**
    1.  **Hate Speech & Insults:** Targeted slurs (racial, homophobic, ableist) and aggressive insults.
    2.  **Violence & Threats:** Explicit threats of physical harm (e.g., "kill you", "bomb", "behead").
    3.  **Self-Harm:** Phrases indicating suicidal intent or self-injury.
    4.  **Sexual Content:** Explicit terms inappropriate for the application.
    5.  **PII (Personally Identifiable Information):**
        * **Email Addresses:** Standard email pattern matching.
        * **Phone Numbers:** Targeted regex for **Pakistani formats** (`+92`, `03xx`).

### Tier 2: Library Fallback (Catch-All)
If the regex checks pass, the system utilizes the `better_profanity` library as a final catch-all for general profanity not explicitly covered by the custom lists.

## 4. API Integration Strategy

The guardrails are integrated into the FastAPI endpoints with distinct flows for Chat and Prediction.

### `/chat` Endpoint
1.  **Input Validation:** The user's `question` is validated **before** it reaches the LLM. If unsafe, the request is blocked immediately, preventing unnecessary inference costs.
2.  **Output Validation:** The LLM's generated response is validated before being sent back to the user to catch any generated toxicity.

### `/predict` Endpoint
1.  **Output Validation Only:** Since the input is an image (processed by Computer Vision), only the text explanation generated by the LLM is validated to ensure the model has not hallucinated unsafe content based on the RAG context.

## 5. Observability & Metrics
The system utilizes **Prometheus** to monitor guardrail performance and violation trends.

| Metric Name | Type | Description | Labels |
| :--- | :--- | :--- | :--- |
| `guard_failures_total` | Counter | Tracks total blocked requests. | `violation_type` (e.g., SEXUAL, VIOLENCE), `source` (user_input/model_output) |
| `guard_latency_seconds` | Histogram | Measures the time taken to run validation (overhead). | N/A |

## 6. Error Handling Workflow
When a violation is detected:
1.  A `ValueError` is raised containing the category (e.g., `UNSAFE:VIOLENCE`).
2.  The application catches this error.
3.  The incident is logged with a warning.
4.  The `GUARD_FAILURES` metric is incremented.
5.  A standardized, safe fallback message is returned to the user:
    > *"I cannot answer that question as it violates safety policies."*
